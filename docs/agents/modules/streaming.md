## 1. Server: producer side (`chat/messaging.py`)

```python
class StreamedMessage(BaseModel):            # :22   cumulative answer text
    content: str

class StreamedMessageSubProcess(BaseModel):  # :26
    source: MessageSubProcessSourceEnum
    has_ended: bool
    event_id: str

```

`ChatCallbackHandler(BaseCallbackHandler)`:

- `ignored_events = [CHUNKING, NODE_PARSING]` for both start and end (`:39`).
- `on_event_start` / `on_event_end` **must be synchronous** (LlamaIndex API) and therefore do
  `asyncio.create_task(self.async_on_event(..., is_start_event=…))` (`:51`, `:65`) — fire and
  forget, no backpressure, exceptions are swallowed.
- `async_on_event` (`:89`): builds `metadata_map`, maps `source = MessageSubProcessSourceEnum[event_type.name]`
  (⚠ `KeyError` if LlamaIndex adds an event type the enum lacks), checks `self._send_chan._closed`
  (private!), then `await self._send_chan.send(StreamedMessageSubProcess(...))` with
  `ClosedResourceError` caught and logged.
- `start_trace` / `end_trace` are no-ops (`:117`).

`handle_chat_message(conversation, user_message, send_chan)` (`:128`):

```
async with send_chan:                       # closes the stream on exit
    engine = await get_chat_engine(ChatCallbackHandler(send_chan), conversation)
    send CONSTRUCTED_QUERY_ENGINE(has_ended=True, event_id=uuid4())
    resp = await engine.astream_chat("Remember - …\n\n" + user_message.content)
    async for text in resp.async_response_gen():
        response_str += text
        if send_chan._closed: return        # client gone
        send StreamedMessage(content=response_str)
    if response_str.strip() == "": send apology
```

⚠ `user_message` is a `schema.Message` instance built by the endpoint (not persisted yet);
`user_message.content` is read directly.

## 2. Server: consumer side (`endpoints/conversation.py:112` `event_publisher`)

```python
send_chan, recv_chan = anyio.create_memory_object_stream(100)     # :110
async def event_publisher():
    async with send_chan:                                        # ⚠ second owner
        task = asyncio.create_task(handle_chat_message(conversation, user_msg_obj, send_chan))
        message_id = str(uuid4())
        message = Message(id=message_id, conversation_id=…, content="",
                          role=assistant, status=PENDING, sub_processes=[])
        final_status = ERROR
        event_id_to_sub_process = OrderedDict()
        try:
            async for obj in recv_chan:
                if isinstance(obj, StreamedMessage):          message.content = obj.content
                elif isinstance(obj, StreamedMessageSubProcess):
                     # merge start/end on event_id, keep first created_at
                     sub = MessageSubProcess(message_id=message_id, source=…,
                                             status=FINISHED if obj.has_ended else PENDING,
                                             metadata_map=obj.metadata_map)
                     event_id_to_sub_process[obj.event_id] = sub
                     message.sub_processes = list(event_id_to_sub_process.values())
                yield schema.Message.model_validate(message, from_attributes=True).model_dump_json()
            await task
            if task.exception(): raise ValueError(...) from task.exception()
            final_status = SUCCESS
        except Exception:
            logger.error("Error in message publisher", exc_info=True)
            final_status = ERROR
        message.status = final_status
        db.add(user_msg_obj); db.add(message); await db.commit()
        final = await crud.fetch_message_with_sub_processes(db, message_id)
        yield final.model_dump_json()
```

Key properties

- Channel capacity 100: if the client stalls, the producer blocks on `send` (backpressure) — no
  unbounded buffering.
- `OrderedDict` keyed by `event_id` gives stable ordering and merges start/end pairs.
- `message.id` is generated by the endpoint (a `str`); SQLAlchemy's UUID type coerces it.
- The final frame re-reads from the DB so ids/timestamps are real.
- The sketch above is simplified: the current `_answer_stream` commits the user message +
  assistant placeholder **before** generation, flushes partial content every ~1.5 s / 200 chars,
  and writes the terminal state (SUCCESS **or** ERROR) in a `finally` block even on disconnect.

**Persistence invariant (fixed 2026-10-27):** `SessionLocal` now uses
`expire_on_commit=False`. Endpoint code copies `assistant_id` / `created_at` before later
commits and `crud.finalise_message` uses the `message_id` argument instead of `message.id`;
reading an ORM attribute after `await db.commit()` triggers an implicit sync lazy load
(`sqlalchemy.exc.MissingGreenlet`) that previously aborted the terminal write, leaving the
assistant row in PENDING. Regression tests live in `tests/app/test_connect_contract.py`.

## 3. Wire format

- `EventSourceResponse` from `sse-starlette==1.6.5`; `sep` defaults to `\r\n`; ping every 15 s
  (`DEFAULT_PING_INTERVAL`) as `: ping - <ts>` comments.
- Frames carry **no event name**; the M2 `fetch` parser treats every `data:` frame as a snapshot
  (named frames are accepted for compatibility).
- Each frame's `data` is one JSON `schema.Message` (see `../API_REFERENCE.md §4`).
- Content is cumulative, so a client can drop intermediate frames safely.

Raw example (two frames, truncated):

```
data: {"id":"b1e0…","conversation_id":"6d8f…","role":"assistant","status":"PENDING","content":"","sub_processes":[{"source":"CONSTRUCTED_QUERY_ENGINE","status":"FINISHED","metadata_map":null,…}],…}

data: {"id":"b1e0…", … "content":"Reliance's FY2025 consolidated revenue was","status":"PENDING", …}

data: {"id":"b1e0…", … "content":"… full answer …","status":"SUCCESS", "sub_processes":[…],"updated_at":"…"}
```

## 4. Client side (M2 — implemented)

`frontend/src/lib/transport.ts` exports `StreamHandlers` (re-exported by `api.ts`):

```ts
export interface StreamHandlers {
  onUserMessage, onAssistantCreated, onSubProcess(stepId, patch), onToken(token),
  onDone({content, sources}), onError(message), onSnapshot?(message)
}
```

`RealTransport.streamMessage` POSTs `{content: question}` with `Accept: text/event-stream` and an
`AbortController`, then reads `response.body.getReader()`. `consumeSseFrames()` handles CRLF, blank-line
boundaries, multi-line `data:`, named events and `: ping` comments. `toChatMessage()` maps each JSON
snapshot; `createSnapshotAdapter()` additionally derives legacy token/trail callbacks from the
cumulative snapshots for compatibility. `onSnapshot` is the preferred store path.

Non-2xx responses are parsed as `ApiError`; a dropped stream performs one `GET /conversation/{id}`
rehydrate with `Last-Event-ID` instead of re-POSTing the question. The store always rehydrates the
canonical thread after `onDone`/`onError`. `MockTransport` emits the same snapshots but only when
`VITE_USE_MOCK=1`.

## 5. Store integration (`store.tsx`)

| Handler | Mutation |
|---|---|
| `onUserMessage` | append the optimistic user message |
| `onSnapshot` | replace the last assistant message with the full mapped snapshot |
| `onAssistantCreated` / `onSubProcess` / `onToken` | compatibility path for handlers without `onSnapshot` |
| `onDone` | mark completed, set final content/sources, clear streaming/cancel, GET canonical thread |
| `onError` | mark failed, toast, clear streaming/cancel, GET canonical thread |

`onSnapshot` is batched with `requestAnimationFrame`, so one SSE frame causes at most one React state
patch; terminal snapshots flush immediately. `stopStreaming()` aborts the fetch, keeps the partial
answer and reloads the persisted thread.

## 6. Testing streaming changes

There is no automated SSE test. Manual loop:

```bash
# 1. backend running with a real conversation
curl -N "localhost:8000/api/conversation/<ID>/message?user_message=What%20was%20FY2025%20revenue%3F"
# 2. confirm persistence + status
curl -s localhost:8000/api/conversation/<ID> | jq '.messages[-1] | {status, len:(.content|length), subs:(.sub_processes|length)}'
```

If you write a test, drive `handle_chat_message` with an `anyio` stream and a stubbed
`get_chat_engine` (patch `app.chat.messaging.get_chat_engine`) — that is the cheapest way to pin
the frame contract without an LLM provider.
